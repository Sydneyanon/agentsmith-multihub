# Compiler-backed ground truth for the reentrancy validator (T-141)

Method: every contract is compiled with **solc 0.8.28 (solcjs)** and executed in a local **@ethereumjs/evm** with a real Solidity attacker contract (`eval/ground-truth/Attacker.sol`) that re-enters once from its `receive`/`fallback` hook, only when enough gas is forwarded (so not under a 2300-gas `transfer`). Exploitable = ether received by the attacker in the re-entrant run exceeds the best honest ordering of the same two calls. Scenarios: attacker credit 1 or 2 ether, amount 1 or 2 ether, victims hold 10 ether. Runs happen in a network namespace with no network (`unshare -rn`). **Foundry was not used**: its release binaries and the official solc binary host are blocked from this environment; the npm `solc` and `@ethereumjs/evm` packages were installed with install scripts disabled into an isolated scratch directory, not into the project.

Corpus validity: all 42 held-out contracts compile with solc 0.8.28 (`compile-corpus.mjs`). This is the first compiler check of the independently authored corpus; before it the Solidity was hand-checked only.

Results (`ground-truth-reentrancy.json`, `ground-truth-counterfactual.json`, `ground-truth-vs-validator.txt`):
- The execution validator agrees with EVM ground truth in **19 of 19** cases (16 corpus cases + 3 counterfactuals); no abstentions.
- EVM-exploitable: `ReentVaultA`, `ReentRewardsA`, `Bank2.cashOut`, `Bank2.withdrawUnchecked`, `Bank2.claimBonus`. Not exploitable: every benign case, and four cases labelled (or intended as) vulnerable: held-out `ReentHelperA` and `ReentBankA`, and dev `Bank.withdrawBad` and `Bank.withdrawHelper`.
- Cause of the four disputes, proven by counterfactual: in each, the state decrement after the call is a checked `-` under Solidity 0.8, so the re-entrant transaction **reverts** (`target call REVERTED`) with attacker credit equal to the amount, and when it does not revert (credit 2, amount 1) the attacker only receives what honest sequential calls would give. Wrapping only that subtraction in `unchecked { }` (`eval/ground-truth/counterfactual/`) makes all three variants EXPLOITABLE in the EVM and the validator agrees.
- Therefore the disagreement with the labels is an **imprecise label** (call-before-update is a vulnerable *pattern*, but not an exploitable drain under checked arithmetic), not a modelling error and not a validator limitation in these cases. The specialist's lead is a legitimate pattern finding; the validator's `weakens` is the accurate challenge.

Limits: bounded scenarios and a single hook depth; one attacker design; a JavaScript EVM rather than Foundry; the corpus labels remain author-asserted for every class other than reentrancy; the counterfactual files are derived from the corpus by wrapping one statement.
