# C5 proposal: oracle selection and generator/evaluator independence

**Status: PROPOSAL for the owner's approval. Nothing here is approved or implemented.** Written 2026-11-28 against commit
`97137c7`. Documentation only: no code, test, schema, secret, image or deployment was changed; nothing was installed, downloaded or
executed; no network call was made. The held-out corpora (`eval/heldout*`, `eval/benchmark-b`, `eval/heldout5`) were not opened.
`eval/dev` was read: it is development data.

**Status words used:** *designed*, *implemented*, *tested*, *integrated*, *demonstrated*, *independently reviewed*,
*operationally verified*, *production deployed*. Everything proposed in this document is **designed** at most. Where existing code
is described, its own status is given.

**Evidence.** Claims about existing code were re-checked in the source at `97137c7` and are cited as `file: symbol`. This document
extends `docs/architecture/c4-c5-tools-and-reproduction-plan.md` (called "the plan" below), Parts 3.2 to 3.4. Where it disagrees
with the plan, it says so.

**The owner's rules this document is written under:**
1. a worker never submits a verdict that the API blindly trusts;
2. the API validates the raw output itself and derives the outcome under a registered evaluator and oracle;
3. all raw outputs and provenance are preserved;
4. no universal independence is claimed from a single oracle;
5. independence is about the underlying method, not component names;
6. a stand-in never counts as real reproduction.

---

## Summary

1. **An oracle is a measurement, and each one measures a different proposition.** Five are assessed: attacker profit, a
   protocol-invariant violation, an unauthorised state change, a privilege gained, and funds locked. No single oracle suits every
   class. Attacker profit is the strongest evidence and the narrowest in reach: it fits ether reentrancy and little else among the
   classes generated today.
2. **A generator's claim and an oracle's proposition are usually not the same statement.** The structural specialists claim a
   *pattern* ("a call before the state update; a re-entering receiver would see stale state"). A profit oracle measures a
   *consequence*. A consequence that is not observed does **not** negate the pattern. The dev corpus contains exactly this case
   (`Bank.withdrawBad`, `Bank.withdrawHelper`: `vulnerable: true, exploitable: false`).
3. **This exposes a tension inside the plan.** The plan's `contradicts` condition (3.4: "the attack sequence executed to its end or
   was rejected by the contract itself; the oracle did not fire") would be satisfied by `Bank.withdrawBad`, whose label is
   `vulnerable: true`. This document proposes a stricter condition: a **refutation witness**, registered per class, that shows the
   contract's own check rejected the claimed mechanism. Without the witness, the result is `weakens` with the recorded reason
   `consequence_not_demonstrated`. It is not a contradiction and it is not a reproduction failure.
4. **Seven classes are generated by the structural specialists; Slither maps detectors onto 12 class names.** Of these, three have
   a fixed oracle that can be written now with a fixture twin (reentrancy with ether, access control, initializer). Four more can
   follow with a fixed oracle (delegatecall, unchecked call, selfdestruct, tx-origin). The rest need protocol-specific setup or
   cannot be reproduced with a fixed oracle and are `unsupported_class` or `unsupported_by_model`.
5. **Independence is partial and must be described as such.** What is independent: compilation by solc, execution by the EVM, and
   the measurement of balances and state through the contract's own interface. What is shared: the parser-derived shared model
   used to aim the test, the function anchor chosen by the generator, the class label that selects the oracle, the people and
   fixtures behind both the specialists and the templates, and (for Slither leads) the solc front-end.
6. **Two existing database behaviours limit what a Foundry result can honestly mean today**, and neither is changed by the plan:
   `hypothesis_independence` counts any `foundry-forge` `supports` as cross-family whoever wrote the test, and both status views
   keep only an evaluator's *latest* evaluation, so a later `inconclusive` re-run hides an earlier `supports`.
7. **Twelve decisions are asked of the owner** (last section). The most consequential: the oracle per class; the refutation-witness
   rule; where oracle registrations are recorded; and whether a `supports` under an unauthorised-state-change oracle is shown at a
   lower effect tier than attacker profit.

## 1. Terms

| term | meaning in this document |
|---|---|
| **claim** | the text and anchor of a hypothesis, as its generator recorded it (`hypotheses.claim`) |
| **pattern claim** | a claim about code structure. Every structural-specialist claim is one (`specialists.ts`, the `claim:` templates) |
| **oracle** | a fixed, versioned procedure that reads EVM-observable state before and after a call sequence and returns *fired* or *not fired* |
| **oracle proposition** | the statement that is true when the oracle fires, in the registered setup. For example: "the attacker's ether balance grew by more than it put in" |
| **refutation witness** | a second fixed, versioned observation showing that the contract's own behaviour rejected the claimed mechanism. Registered with the oracle. Described in section 7 |
| **control** | a run of the same harness without the attack |
| **template** | the fixed test source for one class, with holes for the target's address, selector and arguments |
| **template author** | the deterministic code in the API that fills the holes. Proposed identity `reproduction-template-author` |
| **effect tier** | which kind of consequence an oracle demonstrates: `loss` (profit, funds locked), `control` (privilege gained), `state_change` (an unprivileged write whose importance is a classification, not a measurement) |

## 2. Vulnerability classes that can be generated today

Enumerated from the code, not from documents.

| source | classes | where |
|---|---|---|
| Structural specialists (`solidity-structural-specialists`, family `agentsmith-solidity-parser`) | `reentrancy`, `access-control`, `initializer`, `delegatecall`, `unchecked-call`, `selfdestruct`, `tx-origin` | `analysis/solidity/specialists.ts: FindingClass`; `engine/classes.ts: SPECIALIST_CLASSES` |
| Slither (`slither`, family `slither-ir`), 25 detectors mapped to 12 class names | `reentrancy` (5 detectors: `reentrancy-eth`, `-no-eth`, `-benign`, `-events`, `-unlimited-gas`), `access-control` (`arbitrary-send-eth`, `arbitrary-send-erc20`, `arbitrary-send-erc20-permit`, `protected-vars`, `unprotected-upgrade`), `selfdestruct` (`suicidal`), `delegatecall` (`controlled-delegatecall`, `delegatecall-loop`), `tx-origin`, `unchecked-call` (`unchecked-lowlevel`, `unchecked-send`, `unchecked-transfer`), `uninitialized-state` (3), `divide-before-multiply`, `strict-equality`, `weak-randomness`, `locked-ether`, `missing-zero-check` | `engine/capabilities.ts: SLITHER_DETECTOR_CLASS` |
| Declared but with no deterministic generator | `arithmetic-precision`, `accounting-invariant`, `oracle-manipulation`, `economic-incentive`, `liveness` | `engine/classes.ts: NOT_MODELLED_CLASSES`. The `foundry-forge` capability lists them in `classes`; only an attended Claude session can raise them |

**One class name hides several mechanisms.** Slither's `access-control` class contains `arbitrary-send-erc20` (a token transfer) and
`unprotected-upgrade` (a proxy upgrade). These need different oracles. The oracle must therefore be selected by **(class,
mechanism)**, where the mechanism for a Slither lead is the detector name and for a specialist lead is the class itself. A lead
whose mechanism has no registered oracle is `unsupported_class`, even if its class name has one.

**What the specialists actually claim** (quoted from `specialists.ts`, because the claim decides what a non-firing oracle means):

| class | claim template (abridged) | what the claim entails that an EVM can observe |
|---|---|---|
| reentrancy | "makes an external call … and only afterwards updates … which it relied on before the call; a re-entering receiver would see stale state" | a nested call into the same function, made from the receiver, is accepted on the stale state |
| access-control | "… and no caller-authorisation check dominates that statement" | an unprivileged caller's transaction reaches the statement and its effect persists |
| initializer | "sets … with no caller check and no one-time guard, so any account can call it (again) and take control" | after a legitimate first call, a second call by another account succeeds and changes the value |
| delegatecall | "delegatecalls to …, whose address is …, with no caller-authorisation check before it" | an unprivileged caller makes the contract execute code that caller supplied |
| unchecked-call | "ignores the success flag of a low-level … to …" | with the callee failing, the transaction still completes |
| selfdestruct | "can selfdestruct the contract … and no caller-authorisation check dominates it" | an unprivileged caller's transaction reaches `selfdestruct` |
| tx-origin | "authorises with tx.origin" | a call relayed through another contract is accepted when the privileged account is the transaction origin |

None of these claims says "funds can be stolen". That is why attacker profit cannot be the universal oracle, and why a profit
oracle that does not fire cannot contradict them.

## 3. The oracles

Each oracle is defined over **EVM-observable state only**: ether and token balances, return values, revert data, and storage read
through the contract's own external getters. No oracle may assert on anything derived from the parser.

| id | oracle | proposition when it fires | effect tier | what it needs fixed in advance |
|---|---|---|---|---|
| **O-PROFIT** | attacker profit | the total balance of the attacker-controlled accounts, in the registered asset, is higher after the sequence than before it by at least the registered threshold, and the same measurement is unchanged in the control | `loss` | the asset; every attacker-controlled account; funding of attacker and victims; the threshold; gas price `0` |
| **O-INV** | protocol-invariant violation | a registered relation over the contract's own state holds before the sequence and in the control, and is false after the attack | `loss` or `state_change`, registered per invariant | the relation itself. **The shared model cannot supply it:** `assets_accounting` and `invariants` are `not_computed` (`shared-model.ts`, per `intelligence-model-compatibility.md` 1.1) |
| **O-STATE** | unauthorised state change | a value read through a getter differs after a call by an account that holds no role, and the call did not revert | `state_change` | which getter; the unprivileged actor; the value written |
| **O-PRIV** | privilege gained | after the sequence the attacker can complete a call that reverted for the same attacker before the sequence (behavioural), or a role getter returns the attacker's address | `control` | the role getter or the probe call; the legitimate setup performed first |
| **O-LOCK** | funds locked or denial of service | a withdrawal that succeeds for an honest user in the control reverts after the sequence, **for every registered recovery action** | `loss` | the honest action; the full list of recovery actions tried. The claim is bounded by that list and says so |
| **O-SILENT** | silently accepted failure | with the callee rejecting the call, the transaction completes, the callee's balance is unchanged, and the caller-side state or retained balance has advanced | `state_change` (or `loss` when value is retained) | a rejecting recipient; the value sent |

**Why attacker profit is not enough, and why it is still the best where it applies.** Profit is the only oracle here whose firing
needs no judgement about importance: money moved to the attacker. It is also the hardest to fabricate by accident, provided the
funding is in the control too. But it requires an asset, a victim who holds it, and a path that pays out. Most leads generated
today are about *who may call what*; for those, profit is simply not defined.

**Why O-STATE is weaker, and must be shown as weaker.** The EVM can show that an unprivileged account changed `fee`. It cannot
show that `fee` ought to be protected. That judgement is the generator's classification (or the model's `state.variables[].roles`,
which is parser-derived). The existing bounded validators say the same about themselves: "this shows REACHABILITY by an
unprivileged caller; whether the statement is a privileged action is the specialist's classification, not something execution can
prove" (`challenge.ts: challengeReachability`). The dev corpus shows the judgement is not trivial: `Config.setFeeOpen` is labelled
`vulnerable: true` with the source comment "fee is not an authority var". A `supports` under O-STATE therefore means **"an
unprivileged caller changed X"** and nothing more. Proposal: every evaluation carries its effect tier, and the dossier never renders
a `state_change` result with the wording used for a `loss` result. This is decision OD-4.

### 3.1 Suitability per class

"Now" means a fixed oracle can be written without protocol knowledge and a dev fixture with a safe twin exists. It does **not**
mean it works: no real Foundry has run in this environment (the plan, header).

| class / mechanism | suitable oracle | unsuitable oracle, and why | availability |
|---|---|---|---|
| **reentrancy, ether, single function** (`reentrancy-eth`; specialist `reentrancy` where the call sends value) | **O-PROFIT** (ether). Secondary: a solvency relation over the actors the harness itself created (bank balance ≥ sum of their credits), as O-INV | O-STATE: every withdrawal changes state, so it fires in the control. O-PRIV: no privilege is involved | **now** |
| reentrancy without value, benign, events-only (`reentrancy-no-eth`, `-benign`, `-events`) | O-INV, with a protocol-specific relation | O-PROFIT: no asset moves, so non-firing says nothing | **cannot, with a fixed oracle.** `unsupported_class` until invariants exist |
| cross-function and read-only reentrancy | O-INV or O-PROFIT with a protocol-specific sequence | the single-function template does not exercise the mechanism | **needs protocol-specific setup**; first increment: `unsupported_by_model` |
| **access-control: unguarded write** (specialist) | **O-STATE** on the written variable's getter; **O-PRIV** when the variable is a role (`minters[attacker]`, `owner`) | O-PROFIT: no asset path in general | **now**, for state with an external getter. No getter → `unsupported_by_model` (reading raw storage is forbidden to the oracle: it would need the parser's or compiler's layout) |
| access-control: `arbitrary-send-eth` | **O-PROFIT** (ether), contract funded by a victim | O-STATE | later; fixed oracle, no dev fixture yet |
| access-control: `arbitrary-send-erc20`, `-permit`; `unchecked-transfer` | O-PROFIT in a token, which needs a registered reference token | any oracle without a token | **needs setup:** a vendored reference ERC-20 (and one that returns `false`). It is a stand-in for the *environment*, not the target, and must be registered by hash |
| access-control: `unprotected-upgrade` | O-PRIV after an upgrade | O-STATE alone | **needs protocol-specific setup** (proxy deployment) |
| **initializer** | **O-PRIV:** after the deployer's legitimate call, the attacker's call succeeds and the role getter returns the attacker | O-PROFIT | **now** |
| **delegatecall, caller-supplied target** | **O-PROFIT** with a layout-independent payload that sends the contract's ether to the attacker; or O-PRIV with a payload that writes the owner slot | O-STATE without a payload: there is nothing to read | **later, fixed oracle.** The O-PRIV variant needs the storage layout, which must come from the compiler's artefact, never from the parser |
| delegatecall, stored target set through another entry point (dev: `Misc.fwdImpl` via `setImpl`) | as above, after a two-step sequence | — | **needs model-derived sequence** (which function writes the target). Second increment; until then `unsupported_by_model` |
| **unchecked-call** | **O-SILENT** | O-PROFIT: nobody profits in the basic case (dev: `Misc.ignored`) | **later, fixed oracle** |
| **selfdestruct** | **O-PROFIT:** the contract's ether is forced to the unprivileged caller | *code removed* (`extcodesize == 0`): **unsuitable.** From the Cancun EVM version (EIP-6780) `selfdestruct` no longer removes the code of a contract created in an earlier transaction, and a test framework may apply removal only after the test. The observable effect is the ether transfer | **later, fixed oracle.** The `evm_version` must be in the tool manifest; how the pinned forge reports this is **unverified** until real Foundry runs |
| **tx-origin** | **O-STATE** or **O-PRIV**, with the privileged account as transaction origin calling an attacker contract that relays the call | O-PROFIT in general | **later, fixed oracle.** The precondition ("the privileged user calls the attacker's contract") is a social assumption and is recorded as a limitation. Needs the two-argument `prank` on the cheatcode allow-list |
| `locked-ether` | O-LOCK | O-PROFIT | **cannot be shown by one test.** "No action releases the funds" is a universal negative; O-LOCK shows it only for the registered list of actions. `unsupported_class` in the first increments |
| `strict-equality` | O-LOCK after forcing ether into the contract | — | needs protocol-specific setup |
| `divide-before-multiply`, `arithmetic-precision` | O-INV with magnitudes | every fixed oracle | cannot: needs protocol-specific relations and thresholds |
| `weak-randomness` | O-PROFIT with block manipulation | — | cannot under the proposed cheatcode allow-list (no `warp`, `roll`, `prevrandao`); a separate decision if ever wanted |
| `uninitialized-state` | none generic | — | cannot |
| `missing-zero-check` | **none.** The consequence is an operator's mistake, not an attacker's action | every attacker oracle | **not applicable.** Recorded as `unsupported_class` with reason `no_attacker_action`; never as a failed reproduction |
| `accounting-invariant`, `oracle-manipulation`, `economic-incentive`, `liveness` | O-INV / O-PROFIT / O-LOCK with protocol-specific setup | fixed templates | cannot with a fixed oracle. An attended, human-run test author remains possible (`claude-reproducer`, existing); that is not a preregistered oracle and is outside this proposal |

## 4. Oracle registration

### 4.1 What is fixed before any experiment

A registration is one canonical JSON document, proposed schema `agentsmith-oracle/1`. Everything below is fixed in it. Nothing in
it may depend on a particular lead.

| field | content |
|---|---|
| `id`, `version` | for example `o-profit-ether-reentrancy`, `1` |
| `class`, `mechanisms[]` | which (class, mechanism) pairs it applies to |
| `applicability` | the conditions under which it may be used at all (for example: the anchored function is external or public; the contract is deployable with a no-argument constructor, or with arguments from the registered rule; the function's region has no entry in `unsupported_features`) |
| `proposition` | the plain-language statement that is true when it fires |
| `measurement` | what is read, when, and from which accounts; the comparison; the **threshold** (for O-PROFIT: the minimum profit in wei) |
| `effect_tier` | `loss`, `control` or `state_change` |
| `refutation_witness` | the observation that permits a refutation stronger than `weakens`, or `none` (section 7) |
| `controls[]` | the mandatory control runs and what each must show (section 8) |
| `actors` | the fixed addresses and their roles: deployer, privileged account, victim, attacker, attacker contract, unprivileged bystander |
| `funding` | how much each actor and the target receive, by which cheatcode |
| `argument_rule` | how arguments are chosen (for example: address parameters set to the attacker, then to the privileged account; integers set to the funded amount) |
| `cheatcode_allow_list` | exactly which cheatcodes the template may call. Proposed: `deal`, `prank` (one- and two-argument), `startPrank`/`stopPrank`, `expectRevert`, `label`. Forbidden: `store`, `etch`, `mockCall` and its variants, `warp`, `roll`, `ffi`, every file and environment cheatcode |
| `template_sha256`, `helper_sha256` | the test template and the vendored helper it imports |
| `evm` | the EVM settings the oracle assumes (gas price `0`; the `evm_version` policy) |
| `outcome_rule_version` | the version of the mapping from observations to `supports` / `weakens` / `contradicts` / `inconclusive` |
| `limitations[]` | fixed limitation codes copied onto every evaluation (section 10) |
| `author`, `reviewed_by`, `registered_at`, `source_commit` | provenance (section 5) |

### 4.2 Where it is recorded: existing records first

| record | use | status of the record |
|---|---|---|
| A committed registry in the code (proposed `engine/oracles/registry.ts`) listing each registration and its SHA-256, with a unit test that recomputes the hash | the reviewed source of truth; git history is evidence, outside the database, of when a registration existed | *designed*. The pattern exists: `ANALYSIS_IDENTITIES` is mirrored by the 0016 seed and kept equal by a unit test (`analysis-identity.ts`) |
| `research_blobs` (0007, applied): the registration stored by content hash | immutable storage. The table refuses update and delete, and checks the hash (`research_blobs` constraints; `research_blobs_immutable`) | *designed* for this use. The pattern exists: `engine/decisions.ts: storePolicy` stores `RESEARCH_POLICY_V0` as a blob under `POLICY_SHA256` |
| `workflow_steps.input` of the reproduction step | the oracle hash, template hash, control ids and expected input digest, written when the step is **created**, before it is leased | *designed* |
| `hypothesis_evaluations.input_sha256` | the oracle hash and the outcome-rule version are part of the hashed input, so a changed oracle is a different evaluation key (0015 `hypothesis_evaluation_keys`) | *designed*. Today's hash is `sha256(manifest | tests | match | intent)` (`reproduction.ts: processFoundryValidateStep`) and contains neither |
| the evaluation's stored output blob | the full oracle provenance beside the raw outputs (section 5) | *designed* |

**No migration is needed to start.** "Registered before the experiment" is then shown by three orderings: the registry commit
precedes the run; the blob's `created_at` precedes the step's `created_at`; the step input cites the hash before any lease.

**Honest limit of that evidence.** None of the three is enforced by the database. An operator with the owner connection could
insert a blob and a step in any order (the residual already recorded as S11 in `docs/security/worker-architecture-decision.md`).

**Schema need, named as a draft requiring approval** (not written, not applied; working name `c5-oracle-registry`):
- an append-only table `oracle_registrations` (`oracle_id`, `version`, `content_sha256` referencing `research_blobs`, `class`,
  `effect_tier`, `registered_by`, `registered_at`, `supersedes`);
- a nullable `oracle_sha256` on `hypothesis_evaluations` or on `evaluation_provenance`;
- a trigger refusing a non-`inconclusive` evaluation by an execution-family evaluator unless it cites a registration whose
  `registered_at` is earlier than the creation of the step that produced the evaluation.

It would turn the ordering from process into enforcement. It is **not** required for the local demonstration. Recommendation:
decide it before the first production reproduction (OD-3).

### 4.3 Immutability and versioning

- A registration is never edited. Any change, including a threshold, a funding amount or one cheatcode, is a **new version with a
  new hash**.
- An evaluation is bound to the hash it ran under. Evaluations made under an older version stay as they are and stay labelled
  with it.
- A version found to be wrong (for example, it fires in a control on a fixture) is **withdrawn** by a new registry entry that
  supersedes it. Withdrawal does not delete or rewrite evaluations; it adds a statement that they were made under a withdrawn
  oracle. Any human outcome that relied on one must be re-examined by a human.
- The oracle version is independent of the tool version. `evaluator_version` stays the forge version (`FOUNDRY_VERSION`); the
  oracle enters through `input_sha256` and the stored output. The alternative, an `evaluator_version` such as
  `1.5.1+oracle-0123456789ab` (the shape `capabilities.ts: pinnedVersion` already uses for prompts), is possible without a
  migration and makes the oracle visible in every row. It is offered as part of OD-3.

## 5. Oracle provenance, recorded with every evaluation

Every evaluation produced by a reproduction, **including every `inconclusive` one**, carries a stored output document (proposed
schema `agentsmith-reproduction-evaluation/1`) with at least:

| group | fields |
|---|---|
| oracle | `id`, `version`, `sha256`, `effect_tier`, `proposition`, `author`, `reviewed_by`, `registered_at`, `source_commit` |
| template author | identity, version, analysis family of what it read, `shared_model_sha256`, the model sections read, the facts used (section 6.2) |
| claim scope | the exact proposition this evaluation speaks to, and a statement of what it does **not** speak to |
| execution | the input digest, the tool manifest (the plan, 2.5), the digest of every raw output, who executed and who derived the verdict |
| controls | each control's id and result |
| outcome derivation | the outcome-rule version and the observations that selected the outcome |
| limitations | the registration's limitation codes plus any added at run time |

**Who authored the oracle** is a named person or a named agent session, plus a named reviewer who is not the author. An oracle
written and reviewed by the same party is recorded as `reviewed_by: none`, and that is itself a limitation code
(`oracle_not_independently_reviewed`).

## 6. Generator/evaluator independence

### 6.1 What is shared, and what is not

The generator is taken to be the structural specialists unless stated. "Test author" is the proposed deterministic template author.

| element | shared with the generator? | consequence |
|---|---|---|
| The AgentSmith parser and index, through the shared model (`shared-model.ts`, built by the parser family) | **yes.** The template author reads signatures, guards, roles and state roles from it | a parser misreading can be in the lead **and** in the test |
| The anchor: file, contract, function | **yes.** The generator chose it | if the generator points at the wrong function, the test examines the wrong function |
| The class label | **yes.** It selects the oracle and the template | a misclassified lead is tested against the wrong oracle. Non-firing then says nothing about the real issue |
| The understanding of each class | **yes.** The specialists, the bounded validators, the templates and the oracles are written by the same project | a shared blind spot (a variant nobody thought of) is in all of them |
| The dev fixtures | **yes.** Both were developed against `eval/dev` | results on `eval/dev` demonstrate mechanism, never capability |
| The solc front-end | **no** for the specialists (they do not use solc). **Yes for Slither leads:** Slither reads the solc AST and Foundry compiles with solc. `engine-inventory-and-coordination.md` 4.6 lists both as sharing solc | a Slither lead supported by Foundry is `cross_family` under 0016 and still shares one component |
| The compiled bytecode | no | produced by solc from the sealed source, not by the parser |
| EVM execution | no | performed by forge's EVM |
| The balance, return-data and getter measurements | no | read from the EVM |
| The control run | no | same |
| The verdict derivation | no | a fixed rule over the raw output, run by the API |

**So the honest statement is:** the *verdict* rests on a substrate the generator does not share; the *choice of what to test and
how to reach it* does not. A wrong test can fail to reproduce a real issue. It can also, in one specific way, produce a misleading
`supports`: under O-STATE and O-PRIV the **target of the measurement** (which getter, which role) comes from the parser-derived
model or from the lead. The EVM then truthfully reports a change in something that may not be privileged. That is why those
oracles sit in a lower effect tier.

**Design rule that follows.** Parser-derived facts may be used to **reach** the function. An error there must fail safe: the test
does not compile, or the call reverts in the control, and the result is `inconclusive`. Parser-derived facts may **not** decide
whether the oracle fired. Where the measurement target itself is parser-derived (O-STATE, O-PRIV), the evaluation says so in a
limitation code (`measurement_target_from_model`).

### 6.2 What the template author may and may not read

| may read | from | why it is acceptable |
|---|---|---|
| contract name, file path, function name | the lead's anchor (`lead-identity.ts: LeadAnchor`) | where to aim |
| the class and, for Slither leads, the detector name | the lead | selects the registered oracle; nothing else |
| function signature, parameter types, visibility, payability; constructor parameters | shared model `functions` | how to call; an error is fail-safe |
| existence, name and type of external getters | shared model `state` | what the oracle may read; recorded as `measurement_target_from_model` |
| which account holds a role, and how it is set | shared model `actors_permissions.roles` | which caller is "privileged" in the control |
| `unsupported_features`, `unresolved_questions` | shared model | whether to abstain before writing anything |
| usable remappings | the dependency manifest (`usableRemappings`) | compilation |
| the deployed address of the target | the test itself, at run time | — |

| must never read | why |
|---|---|
| `hypotheses.claim` and `hypotheses.rationale` | the test would encode the generator's reasoning |
| cited line numbers and evidence spans | same; and the lead key deliberately has no line (`lead-identity.ts`) |
| `required_checks`, `alternative_explanations` | generator reasoning |
| any other evaluation of the lead, in particular the bounded validators' traces and reasons | the validators are parser-family; copying their path would launder a parser-family result into an EVM-family verdict |
| any review | opinion |
| Slither's detector description text | generator reasoning |
| `eval/**/labels.json` and any answer key | the template would be fitted to the answer |
| the generator's identity, beyond what the orchestration needs to enforce the family rule | not needed to write a test |

**Enforcement proposed:** the author is a pure function whose input type contains only the left-hand table. A unit test asserts
that the type has no claim, rationale, span, evaluation or review field. The author's stored record lists the facts used.

**An option to reduce the parser dependence, not recommended for the first increment.** Run a compile-only phase first and take
the ABI and the storage layout from the compiler's artefact instead of the parser. Signatures would then be independent of the
parser. The cost is a second round trip to the tools machine and a second worker-reported input. Signature errors already fail
safe, so the gain is in recall, not in integrity. Decision OD-9.

### 6.3 What counts as cross-family evidence under 0016, and what 0016 cannot see

`evaluation_independence.relation` is `cross_family` when the evaluator has role `evaluator`, the generator's family is known, and
the two families differ (`db/migrations/0016_research_independence.sql`; `analysis-identity.ts: evaluationRelation`).
`foundry-forge` is seeded as `evm-execution`, so a Foundry evaluation of any lead from the parser family, `slither-ir`,
`claude-model` or `human` is `cross_family`. `hypothesis_independence.independently_supported` becomes true on one such `supports`.

Three things the view cannot see. **Each was verified in the SQL and the code; none is closed by the plan.**

1. **It does not know the test author.** `analysis_identities.role` allows `generator`, `evaluator` and `abstention` only. The one
   existing test author, `claude-reproducer`, is not in `ANALYSIS_IDENTITIES`. `reproduction.ts: appendReproductionIn` and
   `importTest` refuse only an author whose **id** equals a claim's generator id. So a `claude-hunter` claim tested by
   `claude-reproducer` (same model family, different ids) and run by Foundry is recorded as `cross_family` today.
2. **It does not know the oracle or its controls.** Any `supports` row by `foundry-forge` counts, whatever was asserted.
3. **It keeps only each evaluator's latest evaluation.** Both `hypothesis_status` (0007) and `hypothesis_independence` (0016)
   select `DISTINCT ON (hypothesis_id, evaluator_id)` ordered by the latest event. A later `inconclusive` re-run by `foundry-forge`
   (a timeout, a second oracle that did not apply) replaces an earlier `supports` in both views.

**Proposed rule: what may be recorded as a `supports` by `foundry-forge`.** Because the views count every such row, the conditions
must be applied when the outcome is derived, before the row is written. A `supports` is derived only if **all** hold:

- the forge and solc binaries' hashes equal the committed tool lock (a stand-in therefore never produces one);
- the oracle is registered, applicable to the lead's (class, mechanism), and its hash is in the input digest;
- every mandatory control ran and the oracle did not fire in any of them;
- the oracle fired in the attack run, in both identical runs;
- the test author's analysis family differs from the generator's family, and the author read nothing from the forbidden list;
- the generated test passed the static cheatcode allow-list check.

If any fails, the outcome is `inconclusive` with the code that failed. The row is still written, with all raw outputs.

**Proposed handling of "latest wins".** One reproduction evaluation per (hypothesis, oracle), and a re-run that fails for an
operational reason (`timeout`, `tool_unavailable`, `harness_failed`) is recorded **in the step output only**, not as a new
evaluation, when an evaluation with a definite outcome already exists for the same oracle and input digest. This needs no schema.
It is a rule about when to write a row, and is decision OD-8. The alternative, one evaluator identity per oracle, needs a
migration for every oracle and is not recommended.

### 6.4 Residual dependence that remains after all of the above

Stated so that no one reads "cross-family" as "independent":

1. The anchor and the class come from the generator.
2. The reach (signatures, actors, constructor arguments) comes from the parser-family model.
3. For O-STATE and O-PRIV, the measurement target comes from the model or the lead.
4. The oracles and templates share authorship, assumptions and development fixtures with the specialists and validators.
5. For Slither leads, solc is common to generator and evaluator.
6. Everything runs in a local EVM on the sealed source. Nothing is known about deployed bytecode, configuration, balances or other
   contracts. A contract can also detect a test environment and behave differently in it.
7. Under option D the execution is worker-reported (see `c5-evidence-policy-changes.md`, P2).
8. **One oracle, one sequence.** A `supports` shows one path to one effect. The absence of a `supports` shows nothing about other
   paths. No statement of the form "independently verified" is justified by this design; the supportable statement is
   "reproduced in a local EVM under oracle *X* version *n*, test authored from a parser-family model".

## 7. The refutation witness: when non-firing may be more than `weakens`

**The problem, concretely.** Take the profit oracle on the dev corpus:

| function | label | what happens when the attacker re-enters | profit oracle |
|---|---|---|---|
| `Bank2.cashOut` | vulnerable, exploitable | the nested call is accepted on the stale credit; both payouts persist | **fires** |
| `Bank.withdrawCei` | not vulnerable | the nested call reverts at the contract's own `require` (the balance was already reduced) | does not fire |
| `Bank.withdrawLocked` | not vulnerable | the nested call reverts at the contract's own lock check | does not fire |
| `Bank.withdrawBad` | **vulnerable, not exploitable** | the nested call is **accepted** on the stale balance; then the outer frame's checked subtraction underflows and the whole transaction reverts | does not fire |
| `Bank.withdrawHelper` | **vulnerable, not exploitable** | as `withdrawBad` | does not fire |

The profit oracle gives the same answer for the last four. The first two of them are safe. The last two contain the claimed
pattern, exactly as claimed ("a re-entering receiver would see stale state" is true of them), and are saved only by arithmetic.
An evaluation that called `withdrawBad` "contradicted" would contradict a true claim.

*(This reading of the fixtures comes from reading `eval/dev/contracts/Bank.sol` and `Bank2.sol`, and from the label notes. It has
not been executed: no real Foundry has run in this environment.)*

**The proposal.** Non-firing alone never yields more than `weakens`. A stronger refutation needs a **refutation witness**: an
EVM-observable event, registered with the oracle, showing that **the contract's own check rejected the mechanism the claim
asserts**, on a path the control shows is otherwise usable.

| class | mechanism step | refutation witness (all parts required) |
|---|---|---|
| reentrancy | the nested call from the receiver | the nested call **reverted**, its revert data is not an arithmetic or other `Panic`, and the same call made directly, without re-entry, succeeds in the control |
| access-control, selfdestruct, delegatecall (reachability) | the unprivileged call | the unprivileged call reverted **and** the identical call by the privileged account succeeded in the control (a differential on the caller only) |
| initializer | the second call | the second call reverted **and** the first, legitimate call succeeded in the same run |
| unchecked-call | the failing callee | with the callee rejecting, the transaction reverted **and** with the callee accepting it succeeded in the control |
| tx-origin | the relayed call | the relayed call reverted **and** the direct call by the privileged account succeeded in the control |

This is the EVM counterpart of a distinction the bounded validators already make. `challenge.ts` returns a `counterexample` only
when a control shows the path is executable and the adversarial transaction reverts at an explicit check that negates the
mechanism; a revert from arithmetic or a balance bound is `not-observed`. `pipeline.ts: challengeOutcome` maps the first to
`contradicts` and the second to `weakens`.

**Resulting outcomes** (whether the first row may be `contradicts` at all is proposal P1 in `c5-evidence-policy-changes.md`):

| observation | outcome | recorded reason |
|---|---|---|
| oracle did not fire; refutation witness present; controls passed; both runs agree | `contradicts` if P1 is approved, else `weakens` | `mechanism_rejected_by_contract` |
| oracle did not fire; mechanism step was **accepted**; controls passed | `weakens` | **`consequence_not_demonstrated`** |
| oracle did not fire; the mechanism step was never reached (setup or argument problem) | `inconclusive` | `attack_not_executed` |
| oracle fired; controls passed | `supports` | — |

**The `vulnerable: true, exploitable: false` case is the second row.** It is the correct result of a profit oracle on a function
whose pattern is real and whose consequence is absent. It must be reported as "pattern present, registered consequence not
demonstrated". It must **not** be reported as a reproduction failure, a tool failure, a contradiction, or a false positive of the
generator. In any score of the reproduction step against `eval/dev/labels.json`, these two functions are scored against
`exploitable`, not against `vulnerable`.

## 8. Control design

Every attack run is accompanied by controls. A control uses the **same** harness, deployment, funding, actors and oracle.

| control | what it is | what it rules out | when mandatory |
|---|---|---|---|
| **C-NOOP** | the attack step removed; everything else identical | a measurement artefact: funding counted as profit, a getter that changes on its own, a non-zero gas cost | always |
| **C-HONEST** | an honest sequence of the same calls: a plain account that does not re-enter withdraws its own deposit; the callee accepts the call | a broken harness (the contract did not deploy, the function cannot be used at all); an oracle that fires on ordinary use | always, for O-PROFIT, O-INV, O-SILENT, O-LOCK |
| **C-PRIV** | the same call made by the privileged account | a function that reverts for everyone, which would make "the attacker was rejected" meaningless | always, for O-STATE, O-PRIV, and for any refutation witness that is a differential on the caller |
| **C-TWIN** | the same test against a fixed twin | a template so loose that it fires whatever the code does | **template qualification only.** It needs a known-safe twin, which exists in fixtures and almost never for a real target |

**C-TWIN is not a per-evaluation control and must not be described as one.** It is a gate on the oracle version: before a
version may be used, it must fire on the vulnerable fixture and not fire on the twin, on real Foundry. That qualification result
is recorded with the registration. On a real target there is no twin; the per-evaluation controls are C-NOOP, C-HONEST and C-PRIV.

**When a control itself fails:**

| failure | outcome | code | further effect |
|---|---|---|---|
| a control does not complete (deployment or setup reverts, the honest call reverts) | `inconclusive` | `harness_failed` | none on the lead. Counted per oracle version |
| the oracle fires in a control | `inconclusive` | `oracle_fires_in_control` | never `supports`. **On a fixture, the oracle version fails qualification and is withdrawn** |
| the two identical control runs disagree | `inconclusive` | `non_deterministic` | — |
| the control passed but the attack run failed to compile or run | `inconclusive` | the tool's code | — |

A control failure is never a `supports`, never a `weakens` and never a `contradicts`. The raw output of the failed control is
stored like any other.

## 9. False-positive and false-negative risks, per oracle

"False positive" here means the oracle fires although no real issue of the claimed kind exists. "False negative" means it does not
fire although one does.

| oracle | false-positive risks | false-negative risks | mitigations proposed |
|---|---|---|---|
| **O-PROFIT** | funding counted as profit; the attacker "profits" only its own deposit back; a function that legitimately pays the caller (a reward, a bonus paid once); gas refunds | the exploit needs a different sequence, amount, or a second function (cross-function re-entry); the profit is in a token, not ether; profit exists only above a deposit size the template does not use; **the pattern is real and not exploitable** (`withdrawBad`) | C-NOOP and C-HONEST; profit measured over **all** attacker-controlled accounts net of their funding; a registered threshold; the `consequence_not_demonstrated` reason instead of a refutation |
| **O-INV** | a relation that is not really an invariant of the protocol (it fails on correct code); a relation over the wrong accounts | the violated relation is not the one registered; the relation holds while funds still move | the relation must hold in C-HONEST; relations only over actors the harness created; **no relation taken from the generator**. Protocol relations wait for the `invariants` section of the shared model |
| **O-STATE** | the change is permitted by design (`setFeeOpen`); the "unprivileged" actor is in fact privileged because the model misread the role holder | the state has no getter; the effect is in another contract; the write needs particular arguments | effect tier `state_change`; limitation `measurement_target_from_model`; C-PRIV; abstain when there is no getter |
| **O-PRIV** | the role is meant to be claimable (a first-come initialiser); the probe call is not actually privileged | the role is held in a structure with no getter; privilege is gained in two steps | the legitimate setup is performed **first**, so "claim an unclaimed role" does not fire; the behavioural probe is preferred to a getter |
| **O-LOCK** | the funds are recoverable by an action the list does not contain; the lock is a deliberate pause | the lock needs a state the harness does not reach | the claim is worded as bounded by the registered recovery list; not used in the first increments |
| **O-SILENT** | the call is deliberately best-effort (the specialists already list this as an alternative explanation) | the failure matters only together with later state | effect tier `state_change`; the alternative is recorded as a limitation |
| **all** | a contract that detects the test environment and behaves differently; a template bug | wrong anchor; wrong class; a constructor the author cannot satisfy; an unsupported compiler version; a missing dependency | every operational miss is `inconclusive` with a code, never a refutation; abstention before authoring (`unsupported_by_model`) |

**Asymmetry to keep in view.** Every mitigation above pushes errors toward `inconclusive` and `weakens`. That is deliberate. It
means the reproduction step will have **low recall** on real protocols at first: the plan already expects the first real target to
abstain in several places. Low recall is acceptable; a wrong `supports` or a wrong `contradicts` is not.

## 10. How oracle limitations are recorded

### 10.1 Per evaluation

- **In the stored output** (`agentsmith-reproduction-evaluation/1`, section 5): `limitations[]`, a list of codes with fixed
  meanings, never free text alone.
- **In `hypothesis_evaluations.rationale`** (at most 8000 characters): a fixed first line, so the limit is visible without opening
  a blob. Proposed form:
  `oracle=o-profit-ether-reentrancy@1 tier=loss scope="attacker ether profit by single-function re-entry of Bank2.cashOut" executed_by=worker_reported limits=local_evm_only,single_function_reentry_only,ether_only`
- **For an abstention:** outcome `inconclusive`, rationale prefix `abstained:<code>@<file:line>`, as the plan proposes (3.4).

Proposed initial limitation codes:

| code | meaning |
|---|---|
| `local_evm_only` | sealed source in a local EVM; says nothing about a deployment |
| `single_sequence` | one call sequence was tried |
| `single_function_reentry_only` | cross-function and read-only re-entry were not tried |
| `ether_only` | no token balance was measured |
| `fixed_actor_set` | the actors are the registration's, not derived from the protocol |
| `measurement_target_from_model` | which getter or role was measured came from the parser-family model or the lead |
| `anchor_from_generator` | the function tested was chosen by the generator |
| `effect_is_state_change` | the result shows a write by an unprivileged caller, not a loss |
| `bounded_recovery_list` | O-LOCK only: recovery was tried through a fixed list of actions |
| `social_precondition` | tx-origin: the privileged user must call the attacker's contract |
| `template_fitted_to_dev_fixtures` | the template was developed on `eval/dev` |
| `oracle_not_independently_reviewed` | the registration has no reviewer other than its author |
| `worker_reported_execution` | the execution was not performed or re-performed by the API |
| `consequence_not_demonstrated` | the mechanism was accepted by the contract; the registered consequence did not occur |

### 10.2 In the dossier

The dossier already has the places; no new section is needed (`pipeline.ts: Dossier`, `DossierEntry.provenance`,
`Dossier.limitations`, coverage problems).

| where | what is added |
|---|---|
| each entry's evaluation list | oracle id and version, effect tier, claim scope, limitation codes, control results, `recorded_by` |
| the entry's verdict text | wording per effect tier. The existing text for `contradicts` says "REFUTED in the modelled world" (`pipeline.ts`, the verdict branch). That sentence is about the bounded model and must not be reused for an EVM result |
| `Dossier.limitations` | one standing statement: what a reproduction `supports` means and does not mean (the section 6.4 wording) |
| coverage | a lead whose reproduction abstained or failed is "not examined by reproduction", with the code. A run in which every reproduction abstained reads "completed; nothing reproduced" (the plan, 3.5) |
| a per-run table | per oracle version: attempted, supported, weakened, contradicted, inconclusive by code. This is the raw material for the self-model |

**A naming problem to record, not to fix here.** `hypothesis_status.status` (0007) is `contradicted_by_static_check` or
`weakened_by_static_check` for *any* evaluator's `contradicts` or `weakens`. A Foundry result would carry the label "static
check". The view cannot be changed without a migration. Until then the API and the dossier must present the evaluator's family
beside that status.
